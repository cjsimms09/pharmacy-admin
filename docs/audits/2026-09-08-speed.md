# Speed: the books read one month six times, measured

8 September 2026 · Helper A · branch `work/rebate-month-once`

The owner: *"We need to do what we need to to make sure run faster."*

Measured rather than guessed, on a scratch database seeded at this pharmacy's real scale — 45,782
invoice lines across a year, six suppliers, 1,400 invoices. No real data was used or needed; the
row counts come from `docs/HANDOFF.md`.

**One month of the books went from 491 ms to 32 ms. A twelve-month report went from 4.86 seconds to
0.39.** Every millisecond of it was blocking the whole web server, because the database is a single
serialized connection and no page is served while a query runs.

## What was wrong

`earningSoFar(supplierId, month)` reads the month's invoice lines and works out what that supplier
earned. It does three things per call:

1. reads every invoice line in the month — **with every column**,
2. places **every** line against **every** supplier to decide who owns it,
3. then filters to the one supplier it was asked about.

And it is called **once per supplier**. `loadShared` did
`Promise.all(suppliers.map((s) => earningSoFar(s.id, month)))` for each month in the period, and
`money-position.ts` — the dashboard — did the same. So the same rows were read and re-placed six
times for a month, eighteen for a quarter, and **seventy-two for a twelve-month trend**.

## The measurements

One month, 3,815 lines, each shape timed on its own after a warm page cache:

| | |
| --- | ---: |
| `select *`, one read | 79 ms |
| the six columns actually used, one read | 32 ms |
| `select *` × 6 (one per supplier) | 365 ms |
| six columns × 6 | 179 ms |
| **as the site did it** (`select *` × 6 plus the per-supplier placement) | **491 ms** |

A row has fourteen columns and the calculation reads six of them.

Across the periods a person actually opens:

| Period | As it was | Month read once | Improvement |
| --- | ---: | ---: | ---: |
| a month — the books page, the dashboard | 491 ms | 32 ms | **15×** |
| a quarter | 1,301 ms | 105 ms | **12×** |
| a year — the trend on `/money/report` | 4,860 ms | 430 ms | **11×** |

**Eleven times of that is the repeat read; a further two and a half is `select *`.**

## The index was the small half, and I had it backwards

I went looking for a missing index on `invoice_lines(invoice_date)` — there is one missing, and two
hot paths range-scan the table without it. Adding it moved a month from 491 ms to 371 ms: about a
fifth, against the fifteen-fold from not reading the same rows six times.

So the index is in this branch, because the table only grows and a scan that costs a fifth extra
today is the whole cost once there are three years in it. But it is not the fix, and reporting it as
one would have left the real fault in place looking solved.

## What changed

**`rebate-rates.ts`** — the read and the placement move into `linesForMonth(month)`: one query, six
columns, every line placed against its supplier once, held between requests. `earningForMonth(month)`
returns every supplier's position from that one read. `earningSoFar(supplierId, month)` is now a thin
reading of the same thing, so **every existing caller is unchanged** and gets the improvement for
free — the suppliers page included.

**`profit-and-loss.ts`** and **`money-position.ts`** — the two loops that asked per supplier now ask
once per month.

**A migration** adding `invoice_lines(invoice_date)`.

## The arithmetic that has not changed

Deliberately none of it. The placement rule — identifier first, printed name only where there is
none, and a line that matches neither counted and named rather than dropped — is the same code moved,
not rewritten, and the comment explaining why a substring test was unsafe in both directions moved
with it. The 2,263 tests pass unchanged.

## What is still slow, and whose it is

- **`periodAccount()` and `monthlyTrend()` read every claim once per month** — twelve passes for a
  year. Fixed on `work/money-fold` (#20), not here, to keep the branches apart.
- **`loadDrugDirectory` holds eight full-size copies of the FDA directory at once**, a 430 MB peak
  inside the web server's own process (`docs/audits/2026-09-08-memory.md`). Still the largest single
  number anywhere in the site, and `drug-directory*.ts` is session 1's group.
- **`floorReview()` reads every paid claim with all 42 columns** — 24 MB and a full read at a year,
  warmed on every cold start.
- **`invoices.ts:2221`** asks for one document at a time in a loop. Session 2's file, small list.

## What I would do next, and cannot from here

**Keep the harness.** These numbers took twenty minutes to produce because the scale could be
generated. A `scripts/bench.ts` that seeds a year and times the site's own readings would turn "the
site feels slow" into a table anybody can re-run after a change — the owner's *"make it as efficient
as possible and keep it that way, it will get lots of data every day"* is a standing requirement, and
a standing requirement needs a standing measurement. `scripts/**` is session 1's group.
