# The 835 fix reviewed: the reader is right, and the refusal is invisible

*Helper B (cloud, Session 2's helper), 8 September 2026. Reviewing `x12-835.ts` and
`claim-payments.ts` as they stand on `feature/compliance` at `70c0ca3`, after Helper A took the
three findings in `docs/audits/2026-09-08-835-reconciliation.md` and fixed them.*

I raised those findings and did not write the fix, so this is a review of somebody else's work on
my own report. Everything below was reproduced by running the code, not by reading it.

## What is now right

The three things I said were dropped are read: the payer id from `N1*PR` element 4, `CLP07` as
`controlNumber`, every `CAS` triplet with its loop, and every `PLB` adjustment with the payer's own
reference. `PLB` closes the open claim before it, so a DIR fee no longer lands in the last
patient's `raw[]`.

**And the balance check's arithmetic and sign convention are correct**, which was the thing most
worth getting wrong. `BPR02 = ΣCLP04 − ΣPLB`, so `difference = paid − (claims − adjustments)` is
nought on a file that closes. Confirmed both ways on a synthetic 5010 file: two claims paying
$110.00 gross with a $7.50 PLB deduction and BPR02 of $102.50 gives
`{paidCents: 10250, claimsCents: 11000, adjustmentsCents: 750, differenceCents: 0}` and no problem;
the same file with BPR02 of $110.00 gives `differenceCents: 750` and the reader's own sentence. A
negative PLB — interest paid *to* the pharmacy, which is how `L6` is conventionally written —
also closes: `{paidCents: 11200, claimsCents: 11000, adjustmentsCents: -200, differenceCents: 0}`.

`importRemittance` posts nothing from a file that does not close. That is the fix I asked for and
it works.

## 1. A remittance the reader refused is filed as applied, and says so in words that are wrong

**This is the largest of the three and it is new, because the refusal is what made it matter.**

`importRemittance` returns early on a file that does not close, with `payments: 0` and its
explanation in `problems`. Its only caller —
`src/app/(app)/intake/actions.ts:58` — never reads `r.problems`. It marks the intake item
`status: "applied"`, recategorises the document as a remittance, and writes this summary:

> 0 payments from BIG PBM totalling $0.00, 0 matched to a claim, 0 waiting for theirs. A plan's own
> remittance settles what the claims already carry, so nothing is counted as revenue twice.

The reader's actual sentence — *"This remittance does not add up and nothing from it should be
posted… A segment was not read, and the difference is money"* — is assigned to a variable and
dropped on the floor. So the one case the new check exists to catch is the one case the owner is
told went fine. An 835 with a segment the reader could not read looks, on the inbox, exactly like
an 835 that was empty; and the file is left categorised as a remittance that has been applied, so
nothing will bring it back.

Before the check, a file like this at least posted its claims. Now it posts nothing and reports
success. The check is right; it is the reporting that has to catch up with it.

What it needs: `problems` on the summary whenever it is non-empty, and `status: "failed"` (or a
`needs_review` of some kind) rather than `applied` when nothing was posted from a file that
declared itself unbalanced. `actions.ts` is not my file — I have not touched it.

## 2. The guard cannot fire where BPR02 is unreadable, and the fallback banks the gross

`out.balance` is set only `if (out.totalPaidCents !== null && amounts.length > 0)`, and the refusal
is `if (r.balance && r.balance.differenceCents !== 0)`. So where BPR02 does not parse, `balance` is
`null`, **`problems` is empty — the file does not even say it could not be checked** — and the
refusal cannot fire.

The receipt then banks `r.totalPaidCents ?? out.amountCents`: the sum of the claim payments, which
is **gross**. Reproduced on the same synthetic file with BPR02 unreadable and the $7.50 PLB intact:

```
balance:   null
problems:  []
banked:    $110.00        (the payer sent $102.50)
```

$7.50 of cash the pharmacy never received, on the cash account, with nothing said. That is the
original finding exactly — banking a figure that is not net of the PLB — surviving in the one path
the new check does not cover.

How reachable it is: not very. BPR02 is numeric in every real file, and a file mangled enough to
lose it usually loses its `CLP` segments too, in which case `out.payments` is nought and no receipt
is written at all. It needs BPR02 alone to be unreadable while the claims parse. But the cost if it
happens is money on the books that never arrived, and the fix is one condition: **a file with paid
claims and no readable total cannot be checked, and a remittance that cannot be checked should not
post either.** `balance: null` alongside `payments.length > 0` deserves its own problem sentence.

## 3. A negative PLB makes the receipt say the opposite of what happened

The receipt note is appended whenever `providerAdjustmentCents !== 0`:

> The payer held back **-$2.00** at remittance level (L6 INT4), **which is why this deposit is
> smaller than the claims it settles**. That money is not yet on either account.

Reproduced on a file carrying `PLB*…*L6:INT4*-2.00` with BPR02 of $112.00 against $110.00 of
claims. The deposit is $2.00 **larger** than the claims, because a negative PLB is money added —
interest on a late payment, or an earlier recoupment being given back. Both halves of the sentence
are false, and the file balances, so it posts and the sentence goes on the cash receipt where
somebody reconciling the bank line will read it and be misled in the direction that makes the
deposit look wrong.

`formatCents` prints it as `-$2.00`, so the sentence is at least visibly odd rather than silently
wrong. But "held back -$2.00 … which is why this deposit is smaller" is not something a person
should have to decode at a bank reconciliation. It wants the sign read: *held back* and *smaller*
where the total is positive, *added* and *larger* where it is negative, and the two named
separately where a file carries both.

This one is reachable today. `L6` interest is ordinary on a late remittance, and it is the first
kind of PLB this pharmacy is likely to see.

## One note, not a finding

`N1*PR` reads element 4 as the payer id without reading element 3, the qualifier. That is right
arithmetic — element 4 is the id whatever the qualifier says — but `XV` (the CMS Plan ID) and `PI`
(the payer's own identification) are different namespaces, and the comment calls the id "the join".
Two payers in different namespaces could in principle collide on one string. Worth keeping the
qualifier beside the id before anything joins on it.
