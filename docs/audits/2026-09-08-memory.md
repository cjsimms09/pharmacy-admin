# Memory: what is warmed, what each held reading keeps, and where 1.6 GB is not

8 September 2026 · Helper A · ASSIGNMENTS item 5

The counter had no page for ninety seconds this morning. The site sits at 1.6 GB after a cold start
on a 7.3 GB machine shared with the dispensing system, a browser, Defender and two Claude sessions.

**The headline, and it is not what was expected: the held readings add up to about 128 MB, not
1.6 GB.** Trimming `directoryKeys()` — the hypothesis in the brief, and a real fault — saves about
40 MB. So the readings are roughly a twelfth of the problem, and the fixes that matter are about
**peak** rather than resident: transient arrays that are alive at the same moment as the thing built
from them, one function that holds eight full-size copies of the drug directory at once, and a cache
that never removes anything.

All of it is arithmetic on the row counts already in `docs/HANDOFF.md`. The model is V8 on 64-bit
with pointer compression: a one-byte string is `12 + length` rounded up to 8; an object is
`12 + 4 × fields` rounded up to 8; a `Map` entry is about 32 bytes with its over-allocation and
buckets; an array slot is 4. Every figure below can be re-derived from those four rules.

**Row counts used**, all from HANDOFF's live runs: `drug_directory` 217,773 · `supplier_items`
63,809 · NADAC distinct NDCs 43,396 · product ledger 45,782 · claims 1,081 today on a 21-day archive
and 30,000 at the year the owner is being asked for. The year is the number that matters: every
figure below marked *at a year* is what happens when that history arrives.

## What each held reading keeps

| Reading | Rows | Per row | Resident | Read by |
| --- | ---: | ---: | ---: | --- |
| `directoryKeys()` | 217,773 | 278 B | **58 MB** | `/drugs`, `/products`, `/money/found`, the replay, drug profit |
| `catalogueRows()` | 63,809 | 348 B | **21 MB** | the buy list, `/purchasing`, the ledger, `/suppliers` |
| `allFills()` *at a year* | 30,000 | 588 B | **17 MB** | almost every page |
| `packageSizes()` | ~180,000 | 80 B | **14 MB** | `catalogueRows()` |
| `productLedger()` | 45,782 | 260 B | **11 MB** | `/drugs`, the buy list, the money list |
| `nadacNow()` | 43,396 | 180 B | **7 MB** | pricing everywhere |
| | | | **128 MB** | |

That is the whole base. Every other held reading is derived from these and is smaller.

### The one the brief named, and it is right

`directoryKeys()` holds eight fields for every NDC. Three consumers — `drug-profit-store.ts:114`,
`replay-store.ts:64`, `products-store.ts:27` — read **`key`, `classification` and `otc` only**. The
other five (`teCode`, `genericName`, `strength`, `form`, `labeler`) are read in exactly one place,
`drug-file.ts:488-573`, which is **one drug's page** and its substitution candidates: a handful of
NDCs, not 217,773.

| | Per row | Resident | Saved |
| --- | ---: | ---: | ---: |
| as it is, 8 fields | 278 B | 58 MB | |
| trimmed to `key`/`classification`/`otc` | 120 B | 25 MB | **33 MB** |
| and the keys interned (~40k distinct) | 84 B | 17 MB | **41 MB** |

The interning is worth doing on its own account. Every row's `genericName`, `form` and
`equivalenceKey` arrives as a **fresh string allocation from the driver**, so forty packages of one
drug hold forty copies of the same twenty-two characters. A `Map<string, string>` used to canonicalise
each distinct value as the rows are read costs one pass and collapses the duplicates.

**The drug file keeps what it needs by asking for it.** `drug-file.ts` already works from a small
set of NDCs; a `directoryDetail(ndcs: string[])` that reads the five wide fields for those rows only
is one indexed query per page view, against 41 MB held all day for a page nobody may open.

### Two full scans of the same table, and a third the same size

`directoryKeys()` and `packageSizes()` each run their own `findMany` over all 217,773 rows of
`drug_directory`, and `catalogueRows()` awaits `packageSizes()` — so warming the buy list reads that
table twice. Worse, each query's **rows array is alive at the same moment as the Map built from
it**: 59 MB for `directoryKeys`, 21 MB for `packageSizes`. Those are peaks, not residents, and peak
is what the pharmacist felt.

One pass that returns both maps removes a 217,773-row scan and one of the two transients.

## Where the memory actually is

### 1. `loadDrugDirectory` holds eight full-size copies of the directory at once — a 430 MB peak

`drug-directory-store.ts:31-79`. Alive simultaneously inside one function:

| | |
| --- | ---: |
| the two zips as Buffers | 12 MB |
| `product.txt` + `package.txt` decoded to latin1 strings | 65 MB |
| `parseDirectoryProducts` (~48k × 17 fields) | 21 MB |
| `parseDirectoryPackages` (217,773 × 6) | 36 MB |
| `parseOrangeBook` (~48k × 11) | 13 MB |
| `held = await db.query.drugDirectory.findMany()` — **every row, every column**, line 64 | 106 MB |
| `heldProducts` + `heldPackages` + `heldOrangeBook`, three more derivations of the same rows | 72 MB |
| `rows = buildDirectory(...)`, the new directory | 106 MB |
| **peak in one function** | **430 MB** |

Then it inserts 217,773 rows in 500-row slices inside a transaction, on the event loop, in the web
server's own process. V8 does not hand freed pages back to the operating system promptly, so this
peak becomes the process's resident figure and stays there. **This is the single largest thing in
the site**, and it is the one that most deserves the treatment `scripts/make-claude-copy.ts` already
demonstrates: a child process, whose memory the operating system reclaims completely when it exits.

Two smaller corrections while it is open. Line 64 reads every row **unconditionally**, including
when both files were supplied and nothing held is needed — it is only wanted to rebuild the file
that did *not* arrive. And when it is needed, it wants five columns, not eighteen.

### 2. The held cache never removes anything, and four keys grow without bound

`held.ts` has `FRESH_MS` and `STALE_OK_MS`, and neither evicts. `refreshStale` **recomputes** stale
entries rather than dropping them, and only `forgetHeld(prefix)` deletes — called by imports, for
the prefixes they know they invalidated. `holds` has no cap and no eviction policy.

Four keys make that unbounded rather than merely permanent:

| Key | Grows by |
| --- | --- |
| `books:${period.key}:${today}` | one entry per period **per day**, for ever |
| `recent:${n}:${today}` | one per day |
| `month-account:${m}:${basis}` | one per month ever viewed × 2 |
| `accounts:${basis}:${months}` | one per distinct run of months anybody browses |

Each holds a whole period's object graph. The launcher restarts the app rarely — the tunnel work
established this machine is left running for weeks — so a fortnight adds a fortnight of `books:`
entries that nothing will ever read again and nothing will ever remove. This is the finding whose
shape matches "1.6 GB after it has been up a while", and it is invisible on a cold start.

**Two fixes, both small.** Drop the date from the key and let the fingerprint do its job — that is
what `fingerprint()` is for, and `books:2026-09` re-computed when the data changes is exactly right.
And give `holds` a ceiling: evict the least recently read entry past, say, 40, since `heldStatus()`
already knows the ages.

### 3. `floorReview()` reads every paid claim with all 42 columns

`floor-review.ts:353`. No column list, so every column of every paid claim: 828 B a row, **24 MB at
a year**, warmed on every cold start by `warm.ts` step 11. The nine fields it uses would be 6 MB.

The same shape is in `appeals.ts:110`, `claims.ts:1306` and `money-found.ts:270`. A column list on
each is a one-line change with no behaviour to test.

### 4. I put a year of claims into the cache myself, in the books fold

`accountsFor()` on `work/money-fold` (pull request #20, not yet merged) returned the shared read
alongside the accounts, and `held` pins whatever is returned. `SharedInputs` carries every fill,
every supplier invoice, every invoice line, every stock count and every payment across the span — so
the month's books, the six-month strip and the twelve-month trend would each have pinned their own
copy. At a year that is roughly **90 MB the cache did not previously hold**, and it would have
arrived on the same machine that lost its page this morning.

**Fixed on that branch before it merges.** The books want three fields per fill; the projection is
made inside the held computation so the rows behind it are collectable the moment it returns. Worth
stating plainly because it is the same mistake as the rest of this document, made this morning, by
me: the fold was measured in passes over the claims and not in what it kept.

## What to do, in the order I would do it

1. **Move `loadDrugDirectory` into a child process.** The largest peak in the site by a factor of
   three, and the pattern already exists. Nothing else on this list matters as much.
2. **Cap and evict `holds`, and take the date out of the four keys.** Small, and it is the only
   finding here that grows without bound.
3. **Trim `directoryKeys()` to the three fields the grouping reads**, intern the keys, and give the
   drug file a `directoryDetail(ndcs)` for the five wide ones. 41 MB, and the brief called it.
4. **One pass over `drug_directory` for both maps** instead of two full scans.
5. **Column lists on the four bare `claims.findMany` calls.** 18 MB at a year, no behaviour change.
6. **Consider what `warm.ts` should warm at all.** Eighteen steps run before anybody asks for
   anything, and several — `overNadacNow(28)` and `overNadacNow(7)`, `floorReview()`,
   `productsExtrasNow()` — are pages that may not be opened all week. The scheduler runs this when
   the site is idle, which is right, but a cold start is not idle: it is the moment the pharmacist
   is waiting. Warming the first six and leaving the rest to `refreshStale` on a genuinely idle tick
   would cost nothing anybody notices.

## What would settle it, and what I could not do from here

Every figure above is arithmetic. **One measurement decides which of findings 1 and 2 is the 1.6 GB**,
and it is two lines on the feeds page:

```ts
const m = process.memoryUsage();          // rss, heapUsed, external, arrayBuffers
const n = heldStatus().length;            // how many entries the cache is holding
```

Read them at three moments: straight after a cold start with `warm.ts` finished; after a drug
directory load; and at the end of a working day. If the number is already high at the first, it is
`loadDrugDirectory` and V8's retained peak. If it climbs across the third, it is the cache. If
`heldStatus().length` is in the hundreds, finding 2 is settled on its own.

I would put that on `/tools/data-health` permanently rather than measure it once. A site that has
now twice cost this pharmacy its counter should be able to say how much memory it is using without
anybody attaching a profiler.
