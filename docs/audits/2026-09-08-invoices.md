## 1. An alias typed the way it is printed is stored as two aliases, and then matches nothing

**Severity: this defeats the fix for any supplier whose invoice prints a legal suffix.**

`normaliseAliases()` splits on `[\n,;]`. Aliases are company names, and a company name on an
invoice very often contains a comma — "Independent Pharmacy Cooperative, Inc.", "ANDA, LLC". The
field on the Suppliers page tells the pharmacy to type "the name printed on their invoices", so
typing it exactly is the expected action.

Run on this branch:

```
typed :   "Independent Pharmacy Cooperative, Inc."
stored:   "Independent Pharmacy Cooperative\nInc."
aliasesOf: [ 'Independent Pharmacy Cooperative', 'Inc.' ]

supplierRecordFor([ipc], "Independent Pharmacy Cooperative, Inc.")  -> null
supplierRecordFor([ipc], "INDEPENDENT PHARMACY COOPERATIVE INC")    -> null
```

Both return null because `squash()` strips punctuation from *both* sides before comparing:
`"independentpharmacycooperativeinc"` against a stored `"independentpharmacycooperative"`. Equality
fails. The line stays unplaced — which is the exact failure the branch exists to fix, reached by a
different route. And "Inc." is now a standalone alias on the register, shown on screen, which would
equality-match a line printed literally `Inc.`.

`canonicalSupplier()` does not rescue it: its table has no entry for the long name, so it returns
the string unchanged.

**The two tests disagree with each other about this, and the storage side wins.**

- `tests/suppliers-registry.test.ts` — *"one per line, and commas or semicolons mean another one"*
  asserts `normaliseAliases("Independent Pharmacy Cooperative, IPC Rx; Cooperative")` is three
  aliases.
- `tests/suppliers-registry.test.ts` — *"an alias is matched case- and punctuation-blind, like every
  other name here"* builds its fixture with `row("IPC", null, "Independent Pharmacy Cooperative,
  Inc.")` — the **raw** string, never passed through `normaliseAliases` — and asserts it matches.

The second test passes and protects a row shape that the product cannot produce. That is worse than
no test, because it reads as coverage of exactly the case that is broken.

**This is a decision for session 2, not a patch I should push**, because the first test states the
comma behaviour deliberately. The two options:

- **Newline only** — `raw.split("\n")`. A comma becomes part of the alias, which is what somebody
  copying a name off an invoice means by it. The "one per line" hint on the page already says this.
  Costs the first test its comma and semicolon clauses.
- **Keep the splitter, fix the fixture** — pass the second test's alias through `normaliseAliases`
  so it tests what the product does, and change the page's hint from "One per line" to something
  that warns a comma starts a new name. This keeps the current behaviour and stops the test lying,
  but it leaves the pharmacy one paste away from a broken alias with nothing on screen to say so.

I would take the first. The whole point of the column is "type what the invoice says".

## 3. `emptyInvoiceWarning` is never called on an invoice adopted from the vault

**Severity: the bug it was written to catch survives, through the other door.**

The boundaries session 2 asked about are **right**, and I could not break them:

| `linesStored` | `totalCents` | result |
| --- | --- | --- |
| > 0 | anything | `null` — lines exist, nothing missing |
| 0 | `null` | `null` — no total to be short of |
| 0 | `0` | `null` — an invoice for nothing has nothing missing |
| 0 | negative (a credit memo) | `null` — `<= 0` covers it, so a credit memo is never flagged |
| 0 | positive | the warning, worded differently for a scan |

`if (a.totalCents === null || a.totalCents <= 0) return null` handles the zero, the null and the
negative in one line. A credit memo cannot be flagged as a missing invoice.

**But there are two functions that file an invoice, and only one of them calls it.**

- `fileInvoice()` — `invoices.ts:666`. Calls `emptyInvoiceWarning`, sets `needsReview: true` and
  writes the sentence into `basis`. Correct.
- `adoptDocument()` — `invoices.ts:1533`. This is the path for a PDF already in the vault that
  somebody adopts as an invoice. It reads the text the same way (`textOf`, which returns `null`
  under 200 characters — i.e. for a scan), files the row, and calls the same two line writers at
  `1654` and `1656`. It never calls `emptyInvoiceWarning`. Its last line is:

  ```ts
  return { id, documentId, schedule, needsReview: schedule === "unknown" };   // 1658
  ```

So a scanned invoice adopted from the vault, whose schedule *was* read confidently off the front
page, is filed with a total, **zero lines, and `needsReview` false** — with nothing anywhere saying
so. That is the same failure, with the same consequence (every figure built on invoice lines short
by that invoice and looking complete), reached by a different route.

This matters more than it looks, because **adoption is the likely origin of the live example the
commit cites.** The $1,530.89 invoice with zero lines and `needs_review` already cleared is exactly
what `adoptDocument` produces from a scan; `fileInvoice` would at least have left `needsReview` on
where the schedule was unclear.

**The fix is four lines, mirroring `fileInvoice:666-676`** — capture the two writers' results, call
`emptyInvoiceWarning({ linesStored, totalCents, hasTextLayer: text !== null })`, and on a non-null
answer set `needsReview: true` with the sentence appended to `basis`. `adoptDocument` is session 2's
file and this is a behaviour change on their own new function, so I have not pushed it.

**A query to size it:** `select count(*), sum(total_cents) from supplier_invoices i where
total_cents > 0 and not exists (select 1 from invoice_lines l where l.invoice_id = i.id)` — and the
same with `and needs_review = 0`, which is the count that is actively lying.

## What is sound, and was checked rather than assumed

- **`supplier_id` is a copy, not a new inference.** The migration backfills from
  `supplier_invoices.supplier_id`, which was resolved from the sender address at filing time. Every
  writer of `invoice_lines` sets it: `fileInvoice` (`meta.supplierId`), `adoptDocument`
  (`matched?.id`), `writeInvoiceLines` (`inv?.supplierId`), and `storeModelInvoiceLines`, which
  takes the whole `SupplierInvoice` row so it cannot get it wrong. No path leaves it unset where an
  answer existed.
- **`allSuppliers(true)` in `earningSoFar`** includes retired suppliers, so a line belonging to a
  wholesaler the pharmacy has stopped using is still placed rather than counted as unplaced. Easy to
  get wrong; got right.
- **`extendedCents` is `notNull`** in the schema, so `unplacedCents` cannot become `NaN` on a null.
- **The ordering in `supplierRecordFor` is defensible.** Catalogue name, then register name, then
  alias, then the canonical forms of each. An alias never outranks another supplier's own name, so a
  name typed into the wrong row cannot move a wholesaler's spend onto another's ladder — and there
  is a test that says so.
- **`ranked` sorts by name before every `find`**, so a register that names one wholesaler twice
  gives a stable answer rather than an insertion-order one. This is what the old code lacked.
- **`emptyInvoiceWarning`'s own boundaries**, per the table above: zero, null and negative totals
  all return null, so a credit memo is never flagged as a missing invoice. That was the risk session
  2 named and it is not there.
- **`linesStored: Math.max(written?.read ?? 0, byRule.stored)`** in `fileInvoice` is right: the two
  writers can each store lines the other did not, and taking the larger means a warning is raised
  only when *neither* produced anything. `writeInvoiceLines` really does return `read`.
- **`adoptDocument` refuses to adopt a rebate breakdown, credit memo or statement as an invoice**
  before any of this, which keeps a document recording no receipt of goods out of the Schedule II
  files. That check is sound and is the more dangerous case of the two.
- **The containment analysis in the commit is correct in both directions.** The direction that has
  fired leaves a hole; the direction that has not fired yields a plausible figure on the wrong
  supplier's ladder, which is worse. Replacing it with equality plus a typed alias is the right
  shape.
- **`npm run check` on `feature/compliance` with this merged**: typecheck clean, 2,010 of 2,010
  tests pass, build clean.

## Questions that need the real database

1. **How many supplier names on real invoices contain a comma?** `select distinct supplier from
   invoice_lines where supplier like '%,%'` — names only, no amounts, no NDCs. If the answer is
   none, finding 1 is theoretical and the splitter can stay. If it is IPC and two others, it is the
   whole fix.
2. **How many filed invoices have a positive total and no lines?** The query above, and the same
   restricted to `needs_review = 0`. The second number is the one that is actively lying, and it
   sizes finding 3.
3. **What does `unplacedNames` actually return for the current month?** It is the list the alias
   boxes need filling from, and it exists in memory right now with nothing rendering it. Running
   `earningSoFar` for any supplier and printing that array is the fastest way to finish this change.
