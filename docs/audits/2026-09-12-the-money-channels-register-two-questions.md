# The money-channels register: one thing confirmed clean, two questions

*12 September 2026 — session 2 (cloud). The §3 proactive scan, against
`docs/registers/money-channels.md` (generated 18:48 today) and the code behind it. **No finding.**
Two precise questions and one area confirmed clean, which is what §3 asks for when there is nothing
wrong to report.*

## Confirmed clean: unmatched facilitator money is handled, and handled carefully

The register shows `mtf`: 31 payments, $6,774.31, **31 unmatched**, last 2026-09-11. A 100%-unmatched
channel carrying in-books money is the first thing that looks like a hole, so I went to the code
before writing anything.

It is not a hole. `facilitatorMoney` (`claim-payments.ts:952`) already splits unmatched payments into
`beforeTheFeed` — *"for a prescription dispensed before the daily claims feed begins, never
matchable, so never pending"* — and the rest, and the comment records why:

> *"The owner asked for this once already — 'can we have it stop alerting if looking for a claim
> before 09/01?? this system will never get anything before 09/01' — and it was given to
> `laterPaymentSummary` alone. The dashboard, the MTF page and the money list read this figure
> instead, so all three went on saying '24 not yet matched to a claim' while /claims correctly
> reported none outstanding, over the very same rows."*

So `claim_id IS NULL` is the register's measure and is the right one for the register; it is not the
site's measure of a problem. **Recorded so nobody re-derives it as a finding.**

## Question one: the register says 31, the code's own note says 24

```
OBSERVATION  money-channels.md: mtf, 31 payments, $6,774.31, 31 unmatched, last 2026-09-11.
             claim-payments.ts:990 records "Every one of the 24 is for a prescription dispensed
             before the daily claims feed begins, some as far back as January."
SHOULD BE    A facilitator top-off is paid because of a specific fill — it tops up what a plan paid
             on a prescription the pharmacy dispensed. So a payment for a fill inside the period the
             claims feed covers should find that fill; only one for a fill before the feed began
             cannot.
DIFFERENCE   Cannot be completed from here. 24 of 24 were before the feed when that comment was
             written; there are now 31, and I cannot see which the seven new ones are.
```

Per §6a this is therefore **a question, not a finding**, and it is one query:

```sql
SELECT count(*), sum(amount_cents)
FROM claim_payments
WHERE source = 'mtf' AND claim_id IS NULL
  AND date_filled >= (SELECT min(period_from) FROM claim_imports WHERE period_from IS NOT NULL);
```

Zero means the register's 31 is the known pre-feed case and there is nothing here. Anything above
zero is facilitator money for a fill the site holds, which did not match — and that is worth knowing,
because the most likely cause is already an open finding of mine: `match-remittance.ts`'s level
ladder has no level that keeps the fill number and drops the date, so a service date off by one day
discards the fill number and refuses.

## Question two: no plan remittance has been received for any September fill

```
OBSERVATION  money-channels.md: plan, 9,550 payments, $899,466.98, last received 2026-08-31 — the
             day before the books begin. mtf's last is 2026-09-11. Cash receipts show third_party
             104 receipts, $1,131,521.97.
SHOULD BE    ?
```

**I cannot write the middle line, and I am not going to invent it.** Whether a PBM remittance for an
early-September fill *should* have arrived by 12 September depends on each payer's cycle and on
whether the pharmacy has yet pointed its real 835 feed at the site rather than sending test pulls —
and the owner's own words about the April and June remittances were *"I want to make sure these are
only tests"*. The $899k of `plan` payments is consistent with exactly that.

So it is a question, and a short one: **has a real plan 835 for a September fill arrived yet, and if
one has, is it in?** If the answer is "none has arrived", the register is telling the truth about the
world and nothing is wrong. If one has arrived and is not in, that is a dollar falling between
ingestion and remits — the failure mode §1 names — and it would be worth finding out why.

The reason to ask rather than assume: `third_party` cash receipts stand at $1,131,521.97 across 104
receipts, so deposits **are** being recorded. Money is arriving and being banked. Whether the
remittance that explains each deposit is also arriving is the part I cannot see.
